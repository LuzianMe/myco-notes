# Set up, move or update a notes repository

*Part of the Myco Notes skill: read `SKILL.md` (the folder above) first for `<KIT>`, `<notes>`, `<tools>` and the guard rails, which always apply.*

**When:** A new project, an older flat layout, a folder rename, or a project whose tools are older than the kit.

**First run (method 11.5a): a short conversation, never a silent default.** (1) **Say what you found** in one line: an empty folder, a code project (with or without its own `AGENTS.md`), or a folder of notes (then `adopt.md`). (2) **Ask everything in one message** of numbered questions, recommendation first, and say that "defaults" accepts them all: *where* the notes live (their own repository next to the project, recommended; or this folder, taken over with `--adopt`, which keeps its `AGENTS.md` rules in effect); the *name* and the *owner*, each with a proposed value (the project's own name from its manifest, README or folder; the owner from `git config user.name`), so that "defaults" leaves nothing open; the *time zone* (detect it, ask to confirm); which folders hold *project data* that is not notes (`--data-dir`: inputs, outputs, attachments); and what `notes-commit` does when a *new folder or file* appears in the root (`--new-folders`): `ask` (recommended: it stops and you ask each time), `add` (track and lint as notes), `ignorelint` (track, skip the lint and the map: versioned reference files) or `ignoreall` (neither: inputs, outputs, downloads). Create nothing before the answer. When the notes get their own repository next to a project, also offer (as its own numbered question, recommended yes) one line in the project's `AGENTS.md` (or `CLAUDE.md`) that points agents there, so a session in the project knows the notes exist and updates them; write it only on a yes, as the only change to the project, and commit it there only if the owner says so. For an existing repository whose `.myco-notes.conf` has no `NEW_FOLDERS` line, ask that one question once and add the line.
(3) Run `python3 "<KIT>/tools/bootstrap.py" <dir> --name "Project" --owner "Name" --tz "<zone>" [--data-dir files-input --data-dir files-output] [--new-folders ask|add|ignorelint|ignoreall]` (`python` or `py -3` on Windows; `--layout flat` gives the older arrangement). (4) **Tell the owner where they stand:** it prints the owner's page (`<notes>/getting-started.md`): what they now have, what you do without asking, what needs their yes, their part, the optional protection, what they can say. Relay it in plain words, shortened if the chat is small, without dropping "your part" or the options; do not bury it under tool output. (5) Fill `working-agreement.md` and `state.md` with the owner, and propose the project's main parts as its first areas: new notes about them get an `area: <name>` header line, which the map uses as their group (method 9). Offer the protection steps as numbered choices (a mirror: `MIRROR_TARGET` in `.myco-notes.conf`, then `<tools>/mirror-push`; an encrypted snapshot of it; `<tools>/restore-drill` once); set up only what they choose, and never call a step done that was not.
**Existing repository in the older flat layout, or a folder rename:** `python3 "<KIT>/tools/relocate.py" --root <project>` is a dry run that prints the moves and the path references it would rewrite; show it to the owner, then add `--apply` (on a clean git repository), review `git diff --stat`, run the project's `notes-lint.py`, commit with `notes-commit`. It keeps the folder names the repository uses, refreshes the project's tools and docs from the kit, and updates `.myco-notes.conf`, `.gitignore` and `core.hooksPath`. Run it from the kit, not from the project's own tools folder.
**Updating a project to a newer kit** (the skill was updated, the project's own `<tools>` and `<docs>` copies are still old): run the same `relocate.py --root <project>` from the new kit. When the repository already uses the single folder there is nothing to move, so it only lists and copies the new and changed tool and doc files (never `bootstrap`, the notes, the conf or `AGENTS.md`); then follow what it prints (it also says when the kit has a feature the project has not turned on, such as the map's wiki layout, or review files still kept in `plans/` that now belong in `reviews/` (`relocate.py --root <project> --move-reviews` is a dry run, `--apply` moves them and the paths that name them): offer each in one line, do it only on a yes): lint, build the map, commit, ask the owner for `NEW_FOLDERS` if the conf lacks it, and add the exit-code-3 bullet from `<KIT>/template/AGENTS.md` to `AGENTS.md` if it is missing. Then offer an **upgrade review** (`review.md`, method 21.4): rules the repository does not follow yet (notes without a summary, `<tools>/index --missing`; a newest sync-log line in an older form; tool lines missing from `AGENTS.md`) become proposals of kind `upgrade`, about 20 notes per batch with each summary written out, applied only as the owner confirms. Never rewrite records (logs, archive, inbox, imported, older sync-log lines). Report progress as "N of M notes have a summary".
