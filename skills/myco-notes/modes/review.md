# Review

*Part of the Myco Notes skill: read `SKILL.md` (the folder above) first for `<KIT>`, `<notes>`, `<tools>` and the guard rails, which always apply.*

**When:** "Review the notes", a periodic check, an upgrade review; method section 21.

1. Run `<tools>/index --review-scope`: it says whether a **changed** review (default: the notes changed since the last review's fixes were committed, plus the notes named in the changed lines and the notes pointing to a changed note unless it is a hub) or a **full** one is due (the owner asked for "full", there is no earlier review, or the last full one is older than `REVIEW_FULL_DAYS`, default 30), and lists the notes to read. Read those, not every note, and do what its *Also check* section says (when the kit was updated since the last review: compare `AGENTS.md` with `<KIT>/template/AGENTS.md` and propose the missing lines as `upgrade` fixes; offer each starter note it names as missing in one line, and create it from `<KIT>/template/notes/` only on a yes, fitted to this repository's real facts (an existing mirror, team, data folders) instead of the template's generic lines, with the fitted text shown in the proposal); if nothing changed and nothing is under *Also check*, say so in one line and stop. If you read something and found nothing to propose, still write and commit a short review file (`summary`, `scope`, `open: none`, one paragraph on what you read, no proposals), so the next review starts after it; then say so in one line. Record it as `scope:` in the review file's header. Run `<tools>/notes-lint.py`; read the earlier `<notes>/plans/review-*.md` files (never propose again what the owner declined, unless something changed: then say what).
2. Read the notes for meaning: contradictions between or within notes, claims a later entry replaced, subjects named in several notes without a note of their own, notes about the same thing that do not name each other, many notes without a fixed role or an `area:` header (the map's "Other notes": propose 4 to 8 areas named after the parts of the system and an `area:` line for each such note), gaps (unanswered questions, long-unverified facts, procedures without undo, decisions without reason), lint findings.
3. Write `<notes>/plans/review-YYYY-MM-DD.md` with a header holding `summary:`, `scope:` and `open:` (the numbers still waiting, `none` when all are answered; the lint checks it against the `Status:` lines): one numbered `## N. title` per finding with `Kind:`, `Where:` (files and lines), `Found:`, `Proposed fix:` (the exact text to replace and the new text per file, or the new note in full, in fenced code blocks so the name of a note that does not exist yet is not reported by the lint; a proposed summary as its own `summary: ...` line, at most 200 characters: ready to apply). Run the lint on the review file before showing it: it measures proposed summaries too and `Status: proposed` (plus `Needs: N` when it depends on another). A fix that moves, shortens or deletes text must not leave a note that only it mentioned unconnected: check, and put the link that keeps the note connected into the same proposal (mentions from logs, archive and other records do not count). Commit only this file. Change no note yet.
4. Show the owner a short numbered list (title and one line per fix) and the file's path; they answer per number: yes, no, or a change; "all" accepts everything still proposed.
5. Apply exactly what was accepted, nothing else: **yes** → apply as written, `Status: applied YYYY-MM-DD`; **no** → `Status: declined YYYY-MM-DD: <reason>`, notes untouched; **changed** → rewrite the proposal with their change, `Status: proposed (revised YYYY-MM-DD)`, show it again, apply only on a new yes; a fix whose `Needs:` was declined is rewritten and shown again. Unanswered proposals stay `proposed` (`<tools>/resume` lists them each session); an unattended run applies nothing.
6. Lint and compare with the lint before the review: anything the applied fixes caused (a new orphan, a broken link) becomes a new proposal, not a silent fix. Update the review file's `open:` line, summary and opening paragraph to say what was applied, declined and is still waiting (also in an earlier review file whose carried-over proposal was answered). Add the sync-log line (`- **YYYY-MM-DD review:** applied 1, 3; declined 2; 4 revised, waiting`), commit the touched notes with the review file (`notes-commit --only ...`).
