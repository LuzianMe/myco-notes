# Quick note

*Part of the Myco Notes skill: read `SKILL.md` (the folder above) first for `<KIT>`, `<notes>`, `<tools>` and the guard rails, which always apply.*

**When:** The owner wants a thought, idea or fact remembered; typed or dictated.

Do not run the Capture steps (`capture.md`). Save it in one step: `<tools>/capture --commit "the note"` (in the owner's words, lightly cleaned up; add `--title`, `--tag`, `--related NOTE` only when obvious). It writes one entry at the end of `<notes>/inbox/YYYY-MM.md` (method section 19.1). Then reply in one line ("Saved: <title>"). Ask nothing, verify nothing, add no "not verified" marks (an inbox entry is the owner's statement), touch no other note, add no to-do; never write a secret's value (`capture` refuses one with exit code 4 and writes nothing: say so in one line and offer to save where the secret lives instead). When working through pull requests (a cloud session), push and open the pull request; if `SOLO=1` in `.myco-notes.conf`, squash-merge it yourself once its check passes (`notes-commit --pr --merge` does this where the GitHub CLI exists) and continue from the updated main branch; if the check fails, say why and stop. Do not hold the conversation for a slow check: reply "Saved" as soon as the note is committed and pushed, and merge when the check passes; if `notes-commit` exits 5 because the GitHub CLI cannot reach GitHub here, open and merge the pull request with your own GitHub tools. This cloud and solo flow is experimental (method section 19): when a step of it fails, say so plainly in one line, say what is left for the owner (for example "PR open, not merged"), and do not retry in a loop. Several notes in one session: one entry and one commit each. **Sorting** ("sort my inbox") is separate: move each entry into the note where it belongs using the steps of `capture.md`, then mark the entry `→ moved to <note>.md (YYYY-MM-DD)`; never delete entries.
